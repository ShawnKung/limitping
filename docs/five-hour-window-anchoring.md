# 5 小时窗口锚定说明

本文说明 Codex 5 小时滚动窗口的“锚定”（首次使用起算）机制，以及 `limitping` 如何
判断窗口是否已开始计时、如何用 `ping --until-anchored` 主动让窗口开始计时。

## 背景：窗口按“首次使用”锚定

Codex 的 5 小时额度是滚动窗口，其计时不是从上一个窗口重置的边界自动开始，而是锚定在
**窗口重置后的第一次请求**。在窗口尚未被使用时：

- 后端返回的 `reset_at` 是“假设此刻起算、整段窗口之后到期”的**滚动占位值**，会随当前
  时间一起向后移动；
- 换算出的 `remaining` 恒等于整段窗口长度（5 小时）；
- `used_percent` 因尚无消耗而为 0。

一旦发生首次请求，窗口被锚定：

- `reset_at` **冻结**为“锚定时刻 + 5 小时”，不再随当前时间移动；
- `remaining` 随之低于整段窗口长度，并单调递减。

因此，“窗口是否已经开始计时”与“消耗了多少额度”是两件事：一次极小的请求即可把窗口
锚定并启动计时，但它消耗的额度可能不足 1%，四舍五入后 `used_percent` 仍显示 0。

## `active` 判定

`limitping` 在 `status` 输出和 `limitping_window_active` 指标中给出窗口是否“在计时”。
判据为下列任一成立（且 `reset_at` 晚于当前时间）：

- `used_percent > 0`；或
- `remaining` 明显小于整段窗口长度（即 `reset_at` 已冻结）。

为容忍占位值在秒级换算时的亚秒截断，`remaining` 与窗口长度的比较保留了数秒的余量。
采用该判据后，即使一次很轻的 ping 让 `used_percent` 仍显示 0，只要窗口已被锚定，
`active` 也能正确反映为“在计时”。

实现见 `internal/usage/usage.go` 中的 `windowCounting` 与 `makeWindow`。

## `ping --until-anchored`

当 5 小时额度处于满额（窗口未计时）状态时，可以主动发送请求把窗口“打着”，让它从此刻
开始倒数；这样稍后真正开始工作时可以少等一段时间。

```sh
limitping ping --until-anchored
```

行为：

1. 先回读一次用量。若窗口已经在计时，直接结束，不再发送请求。
2. 否则发送 ping，并在每次 ping 后等待片刻再回读用量，确认窗口是否已开始计时。
3. 为在不过度消耗的前提下提高单轮成功率，起始输入取一个较大的长度，之后每轮把输入
   长度翻倍逐步增加单次消耗；一旦检测到窗口开始计时立即停止，或到达轮数上限后停止。

长输入通过标准输入传给 `codex exec`，避免过长的命令行参数。`--dry-run` 只打印将要执行
的命令，不实际调用模型。

相关参数（起始输入长度、每轮倍增、轮数上限、每轮回读前的等待时长）定义在
`internal/cli/cli.go`，可按后端计量粒度调整。

## 说明

- 让窗口开始计时所需的最小请求大小，取决于后端的计量粒度，可能随时间变化；
  `--until-anchored` 通过“逐轮增大并回读确认”来适应这一点，而非假设某个固定阈值。
- `status` 只读取用量、不消耗额度；实际消耗来自 `codex exec`（包括 `ping`）。
